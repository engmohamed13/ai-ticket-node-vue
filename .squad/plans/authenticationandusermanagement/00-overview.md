## Dependency notes

- **Strictly sequential.** Story 08 imports `backend/src/auth/permissions.ts`, `roles.ts`, and `password.ts` from Story 07 and queries the `users` / `roles` / `permissions` / `role_permissions` / `departments` / `branches` tables Story 07 migrates. Story 09 consumes the exact endpoints and DTO shapes Story 08 exposes.
- **Authentication was explicitly out of scope for both prior features.** See [../projectsetup/00-overview.md](../projectsetup/00-overview.md) (line 21) and [../communicationchannels/00-overview.md](../communicationchannels/00-overview.md) (line 18) — no `User`, `Role`, `Permission`, `Department`, or `Branch` model existed in the working tree before Story 07. The historical Node/Vue implementation (deleted in commit `b1f0b9c`, readable at commit `988127f`) had a bare `User` model with `passwordHash` plus `auth.service.ts`, `auth.controller.ts`, `auth.routes.ts`, `auth.middleware.ts`, and `LoginView.vue`. Each story cites the specific `git show 988127f:<path>` files to learn from; those files are **not** on disk, and their class-based, inline-`res.status()` style is deliberately not reproduced.
- **Story 08 is a breaking change to the existing API.** After it lands, `/api/customers`, `/api/tickets`, and `/api/interactions` all return `401` without a Bearer token, so the Story 06 Communications screen is broken until Story 09 attaches the token. **Deploy Stories 08 and 09 together.** Story 08 also modifies three test suites Story 05 created (`customer.spec.ts`, `ticket.spec.ts`, `interaction.spec.ts`).
- **Shared contract 1 — the RBAC vocabulary.** `PERMISSIONS` (13 keys) and `ROLES` (the six Main Roles from the work item) are declared in `backend/src/auth/permissions.ts` / `backend/src/auth/roles.ts` (Story 07) and **hand-copied** into `frontend/src/types/index.ts` (Story 09) — the same relationship `CHANNELS` already has with `backend/src/channels/types.ts`, since there is no shared package between `backend/` and `frontend/`. Changing a permission key requires editing both sides; `frontend/src/tests/authContract.spec.ts` (Story 09) fails loudly on a one-sided edit.
- **Shared contract 2 — the `AuthUser` DTO.** Declared in `backend/src/services/auth.service.ts` (Story 08), mirrored in `frontend/src/types/index.ts` (Story 09), and returned by `POST /api/auth/login`, `GET /api/auth/me`, and every `/api/users` endpoint. It never contains `passwordHash`.
- **Authorisation model.** One role per user (the work item lists six mutually exclusive Main Roles), permissions attached to roles through an editable `role_permissions` join table, and the permission list baked into the JWT at login so `requirePermission` needs no per-request query. Consequence, called out in both Story 08 and Story 09: a role or permission change takes effect on the user's **next login**, not immediately — `GET /api/auth/me` is the authority for the current state.
- **`CUSTOMER` is more than a permission set.** A `CUSTOMER`-role user is additionally scoped to their own `customers` row via `users.customerId` and `backend/src/auth/scope.ts` (Story 08), because "only my own records" cannot be expressed as a permission. That scoping is what makes the role safe to expose at all.
- **Stateless logout.** `POST /api/auth/logout` returns `200` and the client discards the token; there is no server-side denylist, so a token captured before logout stays valid until it expires (default 8 hours, `JWT_EXPIRES_IN_SECONDS`). This is the single most important known limitation of the design and is documented in both Story 08 and Story 09 — never describe the Logout button as revocation.
- **New required environment variable.** Story 08 adds `JWT_SECRET` (required, minimum 32 characters, **no default**) to `backend/src/config/env.ts`. `env.ts` calls `process.exit(1)` on invalid config, so a deploy or CI run without it dies silently at import time — Story 08 task 1 therefore edits `backend/.env.example` and `backend/src/tests/setup.ts` in the same change.
- **Out of scope across all three stories:** self-service registration, password-reset e-mails, MFA, refresh tokens, server-side token revocation, OAuth/SSO, login rate limiting, editing a user's e-mail, hard-deleting a user (`isActive` soft-deactivation only), creating branches/departments from the UI, i18n (the historical `LoginView.vue` had an Arabic/English toggle; `vue-i18n` is not a dependency and is not added), and reporting/ticket-mutation endpoints — `reports:read` and `tickets:manage` are seeded permissions with no route behind them yet, kept so the Reporting User role is distinguishable in the demo.
